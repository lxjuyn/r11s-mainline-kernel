# R11s v15 预研清单（2026-09-02，基于 v14a/v14b 实测）

> 前置状态：v14b 在机（触摸 ✅ / 蓝牙 ✅ / 显示 ✅ / GPU 3D ❌ / 音频 ❌ / WiFi ❌）。
> 每项含：现象与证据（v14b dmesg 行号见 `recon/v14b_dmesg_full_20260902.log`）、补丁级定位、风险、优先级。
> 本文档为 v14 实测后新增，取代改进方案 §四 中已被实测改写的条目。

## V1 · pclk0_clk_src RCG 不能 latch（新暴露，P1 同族）

- **现象**：`[2.332685] pclk0_clk_src: rcg didn't update its configuration.` ×2（mdp_clk_src 修复后，链条推进到 DSI 像素时钟设定）。
- **机制**：`pclk0_clk_src`（`drivers/clk/qcom/mmcc-sdm660.c:978` 起）父时钟 = DSI PHY PLL（`xo_dsi0pll_dsi1pll_map`）；设频时 DSI PHY PLL 未 prepare/enable → `clk_rcg2.c` `update_config()` 轮询超时。
- **与 B-2 的差别**：父不是 mmcc 内部 PLL 而是 **DSI PHY PLL**——它的 enable 由 DSI PHY 驱动在 mode_set 链中控制，`CLK_OPS_PARENT_ENABLE` 能否驱动 PHY PLL enable **未取证**（PHY PLL 的 prepare 需要整个 PHY 上电序列）。
- **落点**：先审计 `mdss_dsi_ctrl`/PHY 驱动中 PLL enable 与 `pclk` 设频的时序（谁先谁后）；备选 = 在 panel pclk 设定前显式 `clk_prepare_enable(dsi_pll)`。
- **风险**：中。改错时序 → 点屏失败（可回滚内核）。
- **优先级**：**v15 首位**（显示链从"能亮"到"频率内核可控"的关键一步）。

## V2 · GPU 3D：`a512_zap.mbn` 缺失

- **现象**：`[2.285462] adreno_zap_shader_load: *ERROR* Unable to load a512_zap.mbn` → `gpu hw init failed: -2`（pm4/pfp 已在 v14b 加载成功）。
- **已排除**：不把 DTB 的 `.mbn` 改 `.mdt`（`.mbn` direct 路径正确）；主机 linux-firmware 的 `a530_zap.*` 属其他 SoC 代际，**不可混用**（zap 为签名固件，推测不得进入）。
- **来源方向**：① 原厂 OTA 固件区（`R11s_11_OTA_1170.zip` / `NON-HLOS`）再挖；② postmarketOS qcom firmware 包；③ 同 SoC 设备 dump（需来源合法且记录 sha256）。
- **优先级**：中（取决于来源是否可得；找不到则 GPU 3D 长期停在 -2，不影响显示/合成器基本功能）。

## V3 · 音频：ADSP 链未起（cpu dai name 失败）

- **现象**：`sound: deferred probe pending: sdm660-int-sndcard: MultiMedia1: error getting cpu dai name` + `152c0000.audio-codec: deferred probe pending`。
- **机制**：cpu dai = q6asm/q6afe DAI，依赖 ADSP remoteproc 起来 → APR 服务就绪 → q6core。ADSP 本身需 `qcom/sdm660/adsp.mdt`（-2 失败已见日志域）。
- **落点**：① 确认 v14b 上 adsp remoteproc 的实际加载错误行（根因是固件缺失还是 crash）；② 若固件在位但 crash，对表社区 `PIL` 调参经验；③ internal MI2S 端口核对（原 C-1，`q6afe-dai.c`/`q6dsp-lpass-ports.c`）。
- **优先级**：中高（音频整体通路的前置）。

## V4 · WiFi：`vdd-3.3-ch1 not found, using dummy`

- **现象**：`[0.942731] ath10k_snoc 18800000.wifi: supply vdd-3.3-ch1 not found, using dummy regulator`（两轮均有）。
- **机制**：WCN3990 需 `vdd-3.3-ch0` 与 `vdd-3.3-ch1` 两路；v12 手术 DTB 只接了 ch0。ath10k snoc 驱动对 ch1 dummy 的容忍度待验证（此前从未走到固件请求阶段）。
- **落点**：手术 DTB 补 `vdd-3.3-ch1-supply`（与 ch0 同轨或独立轨，需查原厂 DT 的 ch1 定义）；然后固件链路按 A-5/A-6/A-7 推进（`firmware-5.bin` 已就位但版本未取证）。
- **优先级**：中。

## V5 · reboot-reason → fastboot 链路

- **现象**：救援 shell `reboot bootloader` / `reboot -f bootloader` 均正常重启回救援，不进 fastboot（实测两次）。
- **机制**：主线缺下游 `msm reboot reason → IMEM → ABL` 写入链；`CONFIG_NVMEM_REBOOT_MODE=y` 已开但 DTB 侧对应 nvmem 节点/偏移未配。
- **落点**：审计原厂 DT 的 reboot-reason 节点（IMEM 偏移与 magic），在手术 DTB 补 `reboot-mode` nvmem 映射；或接受"按音量下"作为标准流程并在文档固化。
- **优先级**：低（有按键替代方案；改 IMEM 映射有写错内存风险，需谨慎）。

## V6 · 携带项（未变）

- **A-6 固件版本核对**：`wlanmdsp.mbn` 未抽到版本串（签名 ELF），仍「未取证」；WiFi 实测前先跑整组替换判定线。
- **G-E GPU 供电 phandle**（原 B-4 前置）：`rpm-pm660l` 子项无 phandle，需 dtsi 层加标签后才能安全引用；继续**保持 dummy 不瞎指**。
- **D7 双面板兼容 / C-3 树内 DTS 回写**：维持原计划（需 2280 变体实机）。
